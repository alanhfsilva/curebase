# ADR-001: Clinical Trial Participant Capture

- Status: Accepted
- Date: 2026-09-21
- Deciders: Engineering Team
- Project: Curebase Form (CareOps coding exercise)
- Supersedes: ADR-001 draft (in-progress stack sketch)

This document is the detailed second version of the original ADR-001 draft. It records the problem, options, chosen stack, product rules, and operational consequences for v1.

## 1. Context

We need a simple, complete full-stack application that:

1. Collects basic demographic and health-related information through a form.
2. Computes Body Mass Index (BMI) from height and weight.
3. Persists the submitted data and the computed BMI in PostgreSQL.
4. Renders all captured participants in a table.
5. Lets the user filter and paginate that table.

BMI evaluates body weight relative to height (CDC):

- US: `BMI = weight_lb / height_in² × 703`
- Metric: `BMI = weight_kg / height_m²`

v1 is a standalone coding demonstration. It is not the full CareOps SaaS (no workers, AWS, auth, or tenants). Demographics are still treated as PHI in logging and storage practice. This demo is not a HIPAA-compliance claim.

## 2. Problem

The original ADR named a stack but left product and architecture under-specified:

- Where BMI is computed and whether it is stored.
- US vs metric units.
- How list navigation and filtering work.
- Which fields are unique, visible, or validation-bound.
- How the API is layered, tested, and run locally.

Without those decisions, the UI mock and the backend can drift, and clinical math can leak into the browser as the source of truth.

## 3. Options considered

### Option A — Separate git projects

React SPA (`careops-web`) and Fastify API (`careops-api`) as independent repositories, matching the full CareOps layout in AGENTS.md.

- Pros: Matches production CareOps repo boundaries.
- Cons: Two lockfiles, duplicated HTTP contracts, extra CI for a one-form exercise.

### Option B — Single Node process serves UI and API

Fastify serves the React build and `/api` from one package.

- Pros: One deployable, smaller Docker footprint.
- Cons: Mixes frontend and domain in one process; weaker layering story.

### Option C — TypeScript monorepo with npm workspaces (chosen)

One git repository. npm workspaces: `apps/web`, `apps/api`, and `packages/shared` for HTTP Zod schemas and DTOs. Still two runtime processes (Vite + Fastify). BMI is computed only in the API domain layer and stored. Drizzle + PostgreSQL. Docker Compose for Postgres + API.

- Pros: One lockfile and one CI; form and API cannot drift on contracts; layers stay interview-clear; frontend still cannot be trusted for BMI.
- Cons: Workspace plumbing for a small app; two processes to run. No Nx/Turborepo in v1.

## 4. Decision

Implement **Option C**: a TypeScript modular full-stack **monorepo** (npm workspaces), not separate git projects.

```
Browser (React + TypeScript)     apps/web
  → HTTP/JSON                    packages/shared (Zod DTOs)
Node.js / Fastify (routes)       apps/api
  → Application / domain (BMI, unique email)
  → Data access (Drizzle, parameterized SQL)
  → PostgreSQL
```

Preferred implementation path:

| Concern | Choice |
| --- | --- |
| Repo | Single monorepo, npm workspaces |
| Frontend | `apps/web` — React + TypeScript, Vite, React Router, TanStack Query, React Hook Form + Zod |
| Backend | `apps/api` — Node.js + TypeScript + Fastify |
| Shared | `packages/shared` — HTTP Zod schemas and inferred types (create body, list query, list response) |
| Validation | Shared Zod for contracts; API still re-validates at the HTTP boundary; RHF uses the same create schema for UX |
| Domain | BMI and uniqueness live in `apps/api` only — not in `packages/shared` |
| Database | PostgreSQL |
| Data access | Drizzle ORM (in `apps/api`) |
| Local env | Docker Compose (Postgres + API); Vite on the host |
| Testing | Vitest; API/integration tests against Postgres |

Out of v1: update/delete, login, tenants, workers, AWS, Nx/Turborepo, splitting into CareOps multi-repo, canonical metric storage.

## 5. Product rules (v1)

- No authentication. Documented tradeoff, not an invitation to skip PHI logging rules.
- Unique email: one participant row per email; duplicates return 409.
- Age is persisted and shown in the table.
- Units default to US (lbs / inches). Metric (kg / cm) is an opt-in on the form.
- Height/weight are stored as entered, plus `unit_system`. The table labels each row with that row's units.
- BMI is comparable across unit systems and is the filter dimension.
- List: Min BMI / Max BMI filter plus keyset (cursor) pagination. `minBmi`, `maxBmi`, `cursor`, and `direction` live in the URL. Do not use `OFFSET` / page numbers.
- No update or delete endpoints.

## 6. Data model

Table `participants`:

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `first_name` | text | Required; trimmed, length ≥ 1 |
| `last_name` | text | Required; trimmed, length ≥ 1 |
| `email` | citext | Required, unique, email format (`citext` extension) |
| `phone` | text | Required; 10–15 digits after stripping spaces/dashes |
| `age` | integer | Required, 0–120 |
| `weight` | numeric | Required; as entered |
| `height` | numeric | Required; as entered |
| `unit_system` | text | `us` \| `metric`, default `us` |
| `bmi` | numeric(6,2) | Server-computed, persisted, not client-supplied |
| `created_at` | timestamptz | Default `now()` |

Indexes (from access patterns, not guesswork):

- Unique on `email` (constraint).
- `bmi` for range filter.
- `(created_at DESC, id DESC)` for default list order and keyset pagination (id is the uniqueness tiebreaker; `created_at` alone is not unique).

Check constraints: `unit_system` in (`us`, `metric`); `age` 0–120; `weight` and `height` > 0; `bmi` > 0.

No committed participant seed data.

## 7. BMI

Computed only in the API domain service at write time. The client may preview; PostgreSQL stores only the API result.

- US: `(weight_lb / height_in²) × 703`
- Metric: `weight_kg / (height_cm / 100)²`
- Display: 1 decimal. Storage: `numeric(6,2)` so range filters are stable.

Plausible input ranges (reject outside):

- US: weight 50–700 lb, height 20–90 in
- Metric: weight 20–320 kg, height 50–230 cm

## 8. API

Base: JSON, CORS limited to the web origin.

### `POST /participants`

Body:

```json
{
  "firstName": "string",
  "lastName": "string",
  "email": "string",
  "phone": "string",
  "age": 0,
  "weight": 0,
  "height": 0,
  "unitSystem": "us"
}
```

`unitSystem` defaults to `us`. BMI is never accepted from the client. JSON uses camelCase; the database uses snake_case. Create-body, list-query, and list-response schemas live in `packages/shared` and are the source of truth for both apps.

Create validation (Zod):

- `firstName` / `lastName`: trimmed, min length 1
- `email`: valid email
- `phone`: 10–15 digits after stripping spaces and dashes
- `age`: integer 0–120
- `weight` / `height`: numbers in the unit-system ranges in section 7

Success: `201` with the stored participant, including computed `bmi`.

### `GET /participants`

Keyset pagination over `(created_at DESC, id DESC)`. PostgreSQL `OFFSET` is not used: large offsets still scan and discard rows, and concurrent inserts make page N unstable.

Query parameters:

| Param | Type | Rules |
| --- | --- | --- |
| `minBmi` | number | Optional |
| `maxBmi` | number | Optional; if both bounds are set, `minBmi <= maxBmi` |
| `limit` | integer | Optional; default `10`, range 1–100 |
| `cursor` | string | Optional opaque keyset token from a previous `pagination.nextCursor` or `pagination.prevCursor` |
| `direction` | string | Optional `next` \| `prev`; default `next`. `prev` requires `cursor`. |

Sort is always `createdAt` desc, `id` desc. Changing `minBmi` / `maxBmi` drops `cursor` (start of the filtered set).

Cursor payload (encoded URL-safe base64 JSON, not PHI fields): `{ "createdAt": "<ISO-8601>", "id": "<uuid>" }`. Invalid or tampered cursor → 400.

Read `limit + 1` rows to set `hasNextPage` / `hasPrevPage`. Return at most `limit` items.

`total` is an optional `COUNT(*)` with the same BMI filters (not used for navigation). Acceptable at demo scale; not a substitute for the keyset.

Forward page:

```sql
WHERE bmi filters
  AND (created_at, id) < (:cursorCreatedAt, :cursorId)
ORDER BY created_at DESC, id DESC
LIMIT :limit + 1
```

Backward page: the same predicate with `>` and `ORDER BY created_at ASC, id ASC`, then reverse the page in the service so the client always receives desc order.

Query JSON Schema (`GET /participants` query string decoded as an object):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://careops.local/schemas/list-participants-query.json",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "minBmi": { "type": "number" },
    "maxBmi": { "type": "number" },
    "limit": { "type": "integer", "minimum": 1, "maximum": 100, "default": 10 },
    "cursor": { "type": "string", "minLength": 1 },
    "direction": { "type": "string", "enum": ["next", "prev"], "default": "next" }
  }
}
```

Application validation (Zod), not expressible cleanly in the schema above: if `direction` is `prev`, `cursor` is required. First page is `limit` only (`cursor` omitted, `direction` omitted or `next`).

### Errors

| Status | When |
| --- | --- |
| 400 | Validation; field-level messages for the form |
| 409 | Duplicate email |
| 500 | Unexpected; logs contain no PHI |

Layering: `packages/shared` owns HTTP contracts; `apps/api` route parses with those schemas and maps HTTP; `apps/api` service owns BMI and unique-email behavior; Drizzle issues parameterized SQL only.

## 9. UI

Single page, aligned with the attached mock:

- Title: Clinical Trial Participant Capture.
- Dark theme by default; light/dark toggle.
- Form above the table; BMI filters below (and pagination controls).
- Required list states: loading, empty, error.
- Required save states: submitting, success, field/server error.

Form fields: first name, last name, email, phone, weight, height, age. Unit control defaults to US; metric opt-in switches labels to kg/cm.

Table columns: Name, Email, Phone, Age, Weight (unit suffix), Height (unit suffix), BMI (1 decimal), Created.

Empty copy: “No participants yet.” Filtered empty: “No participants match this BMI range.”

Filter + cursor in the URL (`minBmi`, `maxBmi`, `cursor`, `direction`). Pagination controls are Previous / Next (enabled from `hasPrevPage` / `hasNextPage`). There is no page number. Changing the filter clears `cursor` and `direction`. Successful save resets the form to US default and refreshes the list from the start of the current filter (no cursor).

Frontend authorization is not used (no login). The API remains the authority for BMI and uniqueness.

## 10. Local environment

Monorepo layout (one git repository):

```
.
├── package.json              # workspaces: apps/*, packages/*
├── package-lock.json
├── docker-compose.yml        # Postgres + API
├── .env.example
├── apps/
│   ├── web/                  # React SPA (Vite)
│   └── api/                  # Fastify, domain, Drizzle
└── packages/
    └── shared/               # Zod HTTP contracts + inferred types
```

- `apps/web` depends on `packages/shared` for the create-participant schema and list types.
- `apps/api` depends on `packages/shared` for request/response validation. BMI math stays in `apps/api`.
- Root scripts: `dev`, `test`, `lint` orchestrate workspaces. No Nx/Turborepo.
- Postgres is bound to localhost. The API waits for Postgres and runs Drizzle migrations on boot. Vite runs on the host for UI iteration.

No Redis, S3, SQS, EKS, ECS, or Terraform in this exercise. Do not create separate `careops-web` / `careops-api` git repositories for v1.

## 11. Security and PHI

Treat names, email, phone, age, height, weight, and BMI as PHI.

Never:

- Log PHI
- Commit secrets
- Concatenate user-controlled SQL
- Trust the browser for BMI or uniqueness

v1 does not implement authentication, tenant isolation, or resource authorization. That is an explicit scope cut for a local demo, not a production posture.

## 12. Testing

Meaningful tests over coverage percentages.

- Unit: US and metric BMI, rounding (in `apps/api`). Shared Zod schemas: valid/invalid create and list query fixtures.
- API: 400 validation, 409 unique email, persisted BMI, min/max filter, keyset pagination (next/prev, invalid cursor → 400, no `OFFSET`).
- Database: unique email, check constraints.
- Web: form validation, unit-toggle labels, URL filter/pagination state.

## 13. Tradeoffs and operational consequences

- **Monorepo vs separate projects:** one lockfile, one CI, shared HTTP contracts. This exercise does not follow the AGENTS.md four-repo split. Splitting later is an extract of `apps/web` and `apps/api`, not a rewrite, as long as BMI stays in the API.
- **Two processes vs one:** clearer boundaries; slightly heavier local run. Compose covers the API and database. The monorepo does not mean a single deployable.
- **Shared Zod vs duplicating DTOs:** form and API stay aligned; `packages/shared` must not grow domain logic (no BMI formula, no SQL).
- **Store BMI vs compute on read:** writes do extra math; filters and historical display stay stable if the formula later changes. Recalculation would need an explicit migration.
- **As-entered units vs canonical conversion:** no silent unit conversion; table must show a unit suffix so lbs and kg are not mixed unlabeled. Filters still work because they use BMI.
- **Unique email:** simple participant identity; cannot record two captures for the same person without a future upsert or measurement table.
- **No auth:** fastest path to a complete demo; any network peer who can reach the API can read and write PHI. Acceptable only on localhost.
- **Cursor vs OFFSET:** keyset on `(created_at, id)` stays index-friendly as the table grows and does not skip/duplicate rows when new participants are inserted. Tradeoff: no “page 3 of N”; deep links are a cursor, not a page number. `COUNT(*)` for `total` is a separate query and is not used to navigate.

## 14. Consequences for later CareOps work

This v1 is a **monorepo**. It can later be extracted toward AGENTS.md (`careops-web`, `careops-api`, workers, AWS) without moving BMI or persistence into the frontend. Do not fold domain logic into `apps/web` or `packages/shared` to save a round trip.
