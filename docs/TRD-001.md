# TRD-001: Clinical Trial Participant Capture — Technical Requirements

- Status: Draft
- Date: 2026-09-21
- Author: Engineering Management
- Source: [ADR-001](../ADR-001.MD)
- Project: Curebase Form (CareOps coding exercise)

## 1. Purpose

This document translates the decisions in ADR-001 into implementable technical requirements for the v1 Clinical Trial Participant Capture application. It is the contract between architecture and implementation: every requirement here traces back to the ADR, and every implementation task must trace forward to a requirement here.

## 2. System overview

A TypeScript monorepo (npm workspaces) with three packages:

| Package | Runtime | Responsibility |
| --- | --- | --- |
| `apps/web` | Browser (Vite dev, static build) | Form capture UI, participant table, BMI filter, keyset pagination |
| `apps/api` | Node.js (Fastify) | HTTP routes, domain logic (BMI, uniqueness), data access (Drizzle) |
| `packages/shared` | Imported at build time | Zod HTTP schemas, inferred TypeScript types |

PostgreSQL is the sole data store. Docker Compose orchestrates Postgres and the API. Vite runs on the host.

```
Browser (React + TypeScript)        apps/web
  → HTTP/JSON                       packages/shared (Zod DTOs)
Node.js / Fastify (routes)          apps/api
  → Application / domain (BMI)
  → Data access (Drizzle ORM)
  → PostgreSQL
```

## 3. Functional requirements

### FR-1: Participant registration

| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| FR-1.1 | The form collects: first name, last name, email, phone, age, weight, height, unit system | All fields present; unit system defaults to US |
| FR-1.2 | Unit system toggle switches form labels between lbs/inches and kg/cm | Toggling updates labels immediately; no data loss on toggle |
| FR-1.3 | Client-side validation uses the shared Zod `createParticipantSchema` | Invalid submissions are blocked before network request; errors shown per field |
| FR-1.4 | `POST /participants` persists the participant and returns the record with server-computed BMI | 201 response includes `bmi` field; BMI is never accepted from the client |
| FR-1.5 | Duplicate email returns 409 with a user-friendly message | Form displays the conflict error on the email field |
| FR-1.6 | Successful save resets the form to US defaults and refreshes the list from the start of the current filter | Form clears; list reloads without cursor; filter preserved |

### FR-2: BMI computation

| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| FR-2.1 | US formula: `(weight_lb / height_in²) × 703` | Unit test with known input/output pairs |
| FR-2.2 | Metric formula: `weight_kg / (height_cm / 100)²` | Unit test with known input/output pairs |
| FR-2.3 | BMI is computed exclusively in `apps/api` domain layer | No BMI formula exists in `apps/web` or `packages/shared` |
| FR-2.4 | Display: 1 decimal place. Storage: `numeric(6,2)` | Table shows e.g. `24.3`; DB column is `numeric(6,2)` |
| FR-2.5 | Client may show a BMI preview but the stored value comes only from the API | Preview is clearly labeled as estimate; server result is authoritative |

### FR-3: Participant listing

| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| FR-3.1 | `GET /participants` returns a paginated list sorted by `created_at DESC, id DESC` | Default request returns most recent participants first |
| FR-3.2 | BMI range filter via `minBmi` and `maxBmi` query parameters | Filtering returns only participants within the range (inclusive) |
| FR-3.3 | When both bounds are set, `minBmi <= maxBmi` is enforced | API returns 400 if `minBmi > maxBmi` |
| FR-3.4 | Table columns: Name, Email, Phone, Age, Weight (unit suffix), Height (unit suffix), BMI (1 decimal), Created | All columns present; weight/height show the row's own unit suffix |
| FR-3.5 | Empty state: "No participants yet." | Shown when table has zero rows and no filter is active |
| FR-3.6 | Filtered empty state: "No participants match this BMI range." | Shown when filter is active but returns zero rows |
| FR-3.7 | Required UI states: loading, empty, error | All three states implemented and visually distinct |

### FR-4: Keyset pagination

| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| FR-4.1 | Pagination uses keyset cursor on `(created_at DESC, id DESC)` — no `OFFSET` | SQL uses `WHERE (created_at, id) < (:cursor)` pattern, never `OFFSET` |
| FR-4.2 | Cursor is opaque URL-safe base64 JSON: `{ "createdAt", "id" }` | Cursor contains no PHI fields |
| FR-4.3 | Default page size is 10; range 1–100 via `limit` parameter | `limit=0` and `limit=101` return 400 |
| FR-4.4 | Response includes `hasNextPage`, `hasPrevPage`, `nextCursor`, `prevCursor` | Null cursor when no further page exists in that direction |
| FR-4.5 | `direction=prev` requires a `cursor`; omitting cursor with `prev` returns 400 | Validated at the API layer |
| FR-4.6 | Backward page reverses sort internally but returns results in desc order to the client | Client always receives consistent ordering |
| FR-4.7 | Invalid or tampered cursor returns 400 | Malformed base64 or missing fields are rejected |
| FR-4.8 | `total` is a separate `COUNT(*)` with the same BMI filters | Total reflects filtered count, not overall table size |
| FR-4.9 | `minBmi`, `maxBmi`, `cursor`, `direction` live in the URL | Browser back/forward preserves list state |
| FR-4.10 | Changing the filter clears `cursor` and `direction` | New filter starts from the beginning of the result set |

### FR-5: UI chrome

| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| FR-5.1 | Title: "Clinical Trial Participant Capture" | Rendered as page heading |
| FR-5.2 | Dark theme by default; light/dark toggle | Toggle persists visually; no flash on load |
| FR-5.3 | Form above the table; BMI filters and pagination controls below the table | Layout matches the described mock structure |
| FR-5.4 | Pagination controls: Previous / Next buttons | Enabled/disabled from `hasPrevPage` / `hasNextPage` |
| FR-5.5 | No page numbers displayed | No "Page X of Y" anywhere in the UI |

## 4. Non-functional requirements

### NFR-1: Data integrity

| ID | Requirement |
| --- | --- |
| NFR-1.1 | Unique constraint on `email` (citext) — enforced at the database level |
| NFR-1.2 | Check constraint: `unit_system IN ('us', 'metric')` |
| NFR-1.3 | Check constraint: `age` between 0 and 120 |
| NFR-1.4 | Check constraint: `weight > 0` and `height > 0` |
| NFR-1.5 | Check constraint: `bmi > 0` |
| NFR-1.6 | All SQL must be parameterized (Drizzle ORM) — no string concatenation |

### NFR-2: Validation boundaries

| ID | Requirement |
| --- | --- |
| NFR-2.1 | US weight range: 50–700 lb; height range: 20–90 in |
| NFR-2.2 | Metric weight range: 20–320 kg; height range: 50–230 cm |
| NFR-2.3 | Phone: 10–15 digits after stripping spaces and dashes |
| NFR-2.4 | Names: trimmed, minimum length 1 |
| NFR-2.5 | Email: valid email format |
| NFR-2.6 | Age: integer, 0–120 |
| NFR-2.7 | `packages/shared` Zod schemas are the single source of truth for HTTP contracts |
| NFR-2.8 | `apps/api` re-validates at the HTTP boundary even though the client validated first |

### NFR-3: Security and PHI

| ID | Requirement |
| --- | --- |
| NFR-3.1 | PHI fields: first name, last name, email, phone, age, height, weight, BMI |
| NFR-3.2 | PHI must never appear in application logs |
| NFR-3.3 | Secrets must never be committed to the repository |
| NFR-3.4 | CORS limited to the web application origin |
| NFR-3.5 | The browser is never trusted for BMI computation or email uniqueness |
| NFR-3.6 | Error messages (especially 500) must not leak PHI or stack traces to the client |
| NFR-3.7 | No authentication in v1 — documented tradeoff, not an invitation to skip other security controls |

### NFR-4: Performance

| ID | Requirement |
| --- | --- |
| NFR-4.1 | Index on `bmi` for range filter queries |
| NFR-4.2 | Composite index on `(created_at DESC, id DESC)` for keyset pagination |
| NFR-4.3 | `OFFSET` is prohibited — keyset pagination only |
| NFR-4.4 | Read `limit + 1` rows to determine `hasNextPage` / `hasPrevPage` without a second query |

## 5. Data model

### 5.1 Table: `participants`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | PK, default `gen_random_uuid()` |
| `first_name` | text | NOT NULL, trimmed length >= 1 |
| `last_name` | text | NOT NULL, trimmed length >= 1 |
| `email` | citext | NOT NULL, UNIQUE, email format |
| `phone` | text | NOT NULL, 10–15 digits normalized |
| `age` | integer | NOT NULL, CHECK (0–120) |
| `weight` | numeric | NOT NULL, CHECK (> 0) |
| `height` | numeric | NOT NULL, CHECK (> 0) |
| `unit_system` | text | NOT NULL, CHECK IN ('us', 'metric'), DEFAULT 'us' |
| `bmi` | numeric(6,2) | NOT NULL, CHECK (> 0), server-computed |
| `created_at` | timestamptz | NOT NULL, DEFAULT `now()` |

### 5.2 Indexes

| Index | Columns | Purpose |
| --- | --- | --- |
| Unique constraint | `email` | Participant identity, duplicate prevention |
| B-tree | `bmi` | Range filter performance |
| B-tree | `(created_at DESC, id DESC)` | Keyset pagination default sort |

### 5.3 Required extension

`citext` — for case-insensitive email uniqueness.

### 5.4 Seed data

No committed seed data. Tests generate their own fixtures.

## 6. API specification

Base: JSON over HTTP. CORS restricted to the web origin.

### 6.1 `POST /participants`

**Request body** (camelCase):

```json
{
  "firstName": "string",
  "lastName": "string",
  "email": "string",
  "phone": "string",
  "age": 0,
  "weight": 0,
  "height": 0,
  "unitSystem": "us"
}
```

- `unitSystem` defaults to `"us"` if omitted.
- `bmi` is never accepted from the client.

**Responses:**

| Status | Condition | Body |
| --- | --- | --- |
| 201 | Success | Full participant object including computed `bmi` |
| 400 | Validation failure | Field-level error messages |
| 409 | Duplicate email | Conflict error on `email` field |
| 500 | Unexpected | Generic error; logs contain no PHI |

### 6.2 `GET /participants`

**Query parameters:**

| Param | Type | Default | Validation |
| --- | --- | --- | --- |
| `minBmi` | number | — | Optional |
| `maxBmi` | number | — | Optional; `minBmi <= maxBmi` when both set |
| `limit` | integer | 10 | Range 1–100 |
| `cursor` | string | — | Optional opaque base64 keyset token |
| `direction` | string | `"next"` | `"next"` or `"prev"`; `"prev"` requires `cursor` |

**Response:**

```json
{
  "items": [{ /* participant */ }],
  "pagination": {
    "limit": 10,
    "nextCursor": "string | null",
    "prevCursor": "string | null",
    "hasNextPage": true,
    "hasPrevPage": false
  },
  "total": 42
}
```

**Sort:** Always `created_at DESC, id DESC` from the client's perspective.

**Forward page SQL pattern:**
```sql
WHERE bmi_filters
  AND (created_at, id) < (:cursorCreatedAt, :cursorId)
ORDER BY created_at DESC, id DESC
LIMIT :limit + 1
```

**Backward page:** Same predicate with `>` and `ASC` order, reversed in the service layer.

### 6.3 JSON conventions

- Request/response bodies: **camelCase**
- Database columns: **snake_case**
- Mapping occurs in the data access layer

## 7. Package boundaries

These boundaries are non-negotiable architectural constraints:

| Package | May contain | Must NOT contain |
| --- | --- | --- |
| `packages/shared` | Zod HTTP schemas (create body, list query, list response), inferred TypeScript types | BMI formula, SQL, database types, domain logic, service code |

| `apps/web` | React components, hooks, TanStack Query, React Hook Form, Vite config | BMI formula, database access, server-side logic |

## 9. Testing requirements

Tests must be meaningful — no padding for coverage metrics.

### 9.1 Required test categories

| Category | Scope | Examples |
| --- | --- | --- |
| Unit: BMI | `apps/api` domain | US and metric formulas, rounding to `numeric(6,2)`, edge cases at validation boundaries |
| Unit: Schemas | `packages/shared` | Valid and invalid create bodies, list query params, response shapes |
| API: Validation | `apps/api` routes | 400 on invalid fields, correct field-level error messages |
| API: Uniqueness | `apps/api` routes | 409 on duplicate email, case-insensitive matching |
| API: BMI persistence | `apps/api` routes | Created participant has correct BMI stored |
| API: Filtering | `apps/api` routes | minBmi/maxBmi returns correct subset |
| API: Pagination | `apps/api` routes | Next/prev cursors, boundary pages, invalid cursor → 400, no OFFSET in SQL |
| Database | Drizzle + Postgres | Unique email constraint, check constraints reject invalid data |
| Frontend: Form | `apps/web` | Validation feedback, unit toggle label switching, form reset after save |
| Frontend: URL state | `apps/web` | Filter and cursor reflected in URL, browser navigation works |

### 9.2 Test infrastructure

- API and database tests run against a real PostgreSQL instance (not mocked).
- Drizzle migrations run before the test suite.
- Each test manages its own data; no shared seed data across tests.

1. `docker compose up` — starts PostgreSQL (and optionally the API)
2. API waits for PostgreSQL readiness, then runs Drizzle migrations automatically
3. `npm run dev` at root — starts Vite (web) and Fastify (api) via workspace scripts

### 10.3 Required environment variables

| Variable | Purpose | Example |
| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL connection string | `postgresql://user:pass@localhost:5432/curebase` |
| `API_PORT` | Fastify listen port | `3001` |
| `WEB_ORIGIN` | Allowed CORS origin | `http://localhost:5173` |

### 10.4 Excluded infrastructure

No Redis, S3, SQS, EKS, ECS, or Terraform. This is a local-only exercise.

## 11. Out of scope (v1)

These items are explicitly excluded and must not be implemented:

- Update or delete endpoints
- Authentication / login
- Tenant isolation
- Background workers
- AWS infrastructure
- Nx or Turborepo
- Canonical metric storage (converting all values to metric internally)
- Separate `careops-web` / `careops-api` git repositories
- Seed data committed to the repository

## 12. Dependency matrix

```
apps/web ──depends-on──► packages/shared
apps/api ──depends-on──► packages/shared
apps/web ──HTTP──► apps/api
apps/api ──SQL──► PostgreSQL
```

`apps/web` and `apps/api` never depend on each other at build time. Their only contract is `packages/shared` Zod schemas and the HTTP interface those schemas define.
